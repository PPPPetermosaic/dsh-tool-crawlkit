# 架构说明

> 这份文档讲**代码怎么分层、适配器为什么是纯数据**。
> 安装与上手见 [README](../README.md)；具体用法见 [使用指南](使用指南.md)。

---

## 一、分层

```
lib/plugin.js       装配：建 Store、注册六个工具、写加载痕迹
        │
        ├── tools.js        六个工具的定义（参数 schema + 描述 + 渲染）
        │        │
        │        ├── engine.js     执行引擎：跑适配器、分页、去重、续抓
        │        ├── page.js       页面摘要与数据源探测（服务 crawlkit_read / probe）
        │        └── sanitize.js   送进模型前的裁剪与注入清洗
        │
        ├── store.js        落盘：适配器、数据集、续抓游标、失败计数
        │        └── fixtures.js   响应快照（离线重放）
        │
        ├── adapter.js      适配器规范：校验 + 规范化
        │        ├── html.js       HTML 解析 + CSS 选择器引擎
        │        ├── jsonpath.js   极简 JSON 路径
        │        └── urlparams.js  URL 占位符（解析 + 填充）
        │
        └── http.js         网络：抓取、编码判定、cookie、风控识别
                 └── failure.js   失败分类、阈值升级
```

**依赖方向是单向的**，没有循环。这带来一个具体好处：
`urlparams.js` 被抽成独立的叶子模块，正是因为 `adapter.js` 要校验 URL 需要哪些参数，
而 `engine.js` 要填值——若把工具函数放进 `adapter.js`，模块图会绕成循环。

## 二、为什么适配器是"数据"而不是"代码"

| | 代码式规则 | 数据式适配器（本项目） |
|---|---|---|
| 能审查 | 要读代码 | 一眼看懂，能 diff |
| 能分享 | 有安全风险 | 直接贴给他人 |
| 生成它 | 要执行代码 | 不需要执行任何东西 |
| 仓库干净 | 站点知识混进代码 | 站点知识天然落在插件之外 |

**规则里不允许出现脚本** —— 没有逃生门，这是刻意的选择。

这条约束带来三个连带设计：

1. **包里不内置任何站点适配器** —— 否则仓库会混进站点知识，且很快过期
2. **适配器是纯 JSON**，所以 `crawlkit_adapter` 的 `template` 动作能直接给出可改的骨架
3. **校验做得细** —— 规则由 agent 现场生成，写错时若静默通过，表现就是
   "跑通了但 0 条数据"，而 0 条数据恰恰是最难排查的形态

## 三、两条通道与它们的边界

**HTML 通道**：`html.js` 里的 tokenizer + 选择器引擎。
自己实现而不用第三方库，是为了零依赖；代价是只支持抓取真正用得上的选择器语法
（见 [使用指南](使用指南.md) 的选择器范围）。

**JSON 通道**：`jsonpath.js`，只实现 `data.list`、`data.list[0]`、`data.list[*]`、
`owner.name` 这几种形态。不做过滤表达式、不做函数——那些是另一套语言，不是抓取必需。

**为什么要两条**：当下主流站点把数据放在接口里，页面 HTML 只是空壳。
没有 JSON 通道，这类站点一个都抓不了。

**空壳页必须单独判**：走 HTML 通道撞上空壳时，报"改选择器"是错的方向——
`http.js` 的 `detectClientRendered` 会识别出"这一页 HTML 里根本没数据"，
直接让调用方改抓接口。

## 四、几个刻意的取舍

### 1. 失败分类独立成模块

抓不到时，报出来的**原因**比"抓不到"本身更重要。`failure.js` 存在的唯一理由是
**止住重试循环**：单次超时又长，若每次都回一句"换个参数再试"，
`超时 × 重试次数` 会累加成十几分钟空转。

### 2. "命中 0 条"必须显式失败

成熟爬虫库里选择器没命中通常静默返回空，而 agent 生成适配器时最需要的
恰恰是"你这条选择器一条都没命中"这个信号。没有它，生成适配器就是空话。

### 3. 数据目录跟着会话工作区

适配器、数据集、快照都写在**当前会话的工作区**下，而不是插件的进程目录或安装目录。
这样插件目录永远干净（更新插件不会碰数据），用户也总能找到自己的数据。

代价是一个使用陷阱：**换个工作目录开会话就看不到之前的数据**。
所以要共用一份数据时用绝对路径的 `dataRoot`。

### 4. 展示层与落盘分离

`sanitize.js` 的裁剪与注入清洗**只作用于送进模型的文本**；
落盘的数据保持原文。这两件事混在一起，用户拿到的数据就会被展示层的防护改写。

## 五、验证方式

包自带一个自检入口，不依赖 DSH、不联网、不写任何文件：

```
node check.js
```

它守三类**静默失败**：

| 守什么 | 不守会怎样 |
|---|---|
| 注册补丁的 name 与包名不一致 | 插件装上但**完全不生效**，且没有报错 |
| `lib/` 下某个模块加载不了 | DSH 只报 `failed to import`，不说清是哪个文件 |
| 工具的参数或输出 schema 不合法 | DSH 拒绝加载整个插件，错误指向编译结果而非原始定义 |

运行环境是另一回事，那要用 `crawlkit_selfcheck`（在 DSH 里跑）。
两者检查的对象不同，都需要。
